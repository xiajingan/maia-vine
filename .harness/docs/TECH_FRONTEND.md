# 前端技术方案规范

> 专用于 `frontend-design` 任务。技术方案服从本次 PRD、设计产物、项目 `ARCHITECTURE.md` 和 `config/technology.yml`，以最小前端变更还原用户场景。
> 视觉 token 与项目采用的组件基线见 [UI_DESIGN_SYSTEM.md](UI_DESIGN_SYSTEM.md)，编码与联调见 [CODING_FRONTEND.md](CODING_FRONTEND.md)。

**产出物**：保存至 `docs/tech-docs/`，更新项目自有的作用域注册表 `index.md`，以 frontend 类型登记模块、实际涉及的表/API/组件和 Story/AC。

**文档边界**：单份不超过 500 行，禁止用大段代码代替设计。只描述本次变化；框架、状态库、路由、样式和组件模式均从项目配置读取，不把默认 Vue Profile 当成跨项目硬约束。

**渐进式加载**：先按技术方案索引的模块、表/API、组件和 Scope Key 找到 current(`verified`) 条目，再读本次 PRD/设计、Architecture、technology 配置、受影响代码和强相关历史方案。

**版本边界**：新 Sprint 创建新技术方案，不改写旧 Sprint 产物；Exec 以当前 Task/Run 登记 frontend `draft` 并用 `Supersedes` 指向 current Entry，Review PASS 后由 Runtime 发布并更新旧条目状态。

每份技术方案必须包含唯一的 `## 作用域清单`，并与 `docs/tech-docs/index.md` 当前 Task/Run 登记逐行一致；不适用的表/API 或组件写 `—`，两者不能同时为空：

| Scope Key | 模块 | 表/API | 组件 |
|-----------|------|--------|------|
| tech:example | example | example-api | ExampleView |

## 最高原则：最小充分前端设计

1. **场景保真**：页面、组件和状态变化必须关联 PRD 行为或 AC。
2. **现状优先**：先复用既有页面、组件、数据获取和交互模式；新增项说明现状不能承载的原因。
3. **职责就近**：行为、状态和副作用留在最接近其稳定拥有者的位置。
4. **抽象有据**：不因视觉相似或减少行数创建通用组件；抽象必须有稳定语义和真实消费者。
5. **单一真源**：服务端、URL、Store、表单和局部 UI 状态不得互相复制为多个可写真源。
6. **复杂度最低**：同样满足交互和质量目标时，选择新增组件、全局状态、依赖和层级更少的方案。
7. **配置服从**：框架专属写法仅在 `config/technology.yml` 选择对应 Profile 时适用。

## 组件抽象与复用

### 复用阶梯

`Design Token → 基础控件 → 交互模式 → 领域组件 → 页面组件`

| 层级 | 复用判断 | 所有权 |
|------|----------|--------|
| Design Token | 同一视觉语义应统一 | Design System |
| 基础控件 | 无业务语义，行为稳定，可主动标准化 | 项目 UI 基础层 |
| 交互模式 | 相同交互语义和状态模型，存在真实复用 | 项目 UI/feature shared |
| 领域组件 | 同一领域概念和业务行为 | 拥有该语义的 feature/domain |
| 页面组件 | 为具体流程编排，默认不跨场景复用 | 页面/feature |

### 抽象门槛

- 视觉相似不等于语义相同；不同领域规则不得塞进同一万能组件。
- 基础控件可按 Design System 建立；领域组件通常在出现真实第二消费者且变化方向稳定后提取。
- 第一次复用优先组合既有控件；不要预判所有 variants、slots 或配置项。
- Props/inputs 表达稳定变化点，events/outputs 表达领域无关结果；避免传递整个大对象或巨型配置。
- 组件只为了缩短文件或“以后可能复用”而拆分时，应保留在当前拥有者中。
- 跨 feature 提取前写明消费者、共同语义、差异点、所有权和回归范围。

## 状态所有权与状态图

状态不是默认放入全局 Store 的树，而是由不同真源构成的所有权图。

| 状态类别 | 默认真源/位置 | 关键约束 |
|----------|---------------|----------|
| 服务端状态 | 项目数据访问/查询层 | 缓存、失效和并发语义统一管理，不长期复制到 Store |
| URL/导航状态 | Router/URL | 可分享、刷新可恢复的筛选与定位优先放 URL |
| 跨页面持久状态 | 项目声明的 Store/持久层 | 只有稳定跨页面所有权时提升 |
| Feature 共享状态 | feature 范围 Store/composable | 不泄漏到无关 feature |
| 表单状态 | 表单或表单模型 | 提交前不与服务端实体形成双向可写副本 |
| 临时 UI 状态 | 最近的组件/composable | loading、展开、hover 等不默认全局化 |
| 可推导状态 | 不存储 | 从唯一真源计算，避免同步逻辑 |

### 状态设计原则

- 状态归最接近的稳定拥有者；只有跨稳定边界共享时才上移。
- 单向数据流优先；写入口、生命周期和清理时机明确。
- 区分“首次加载、刷新、提交、局部失败”等真实可观察状态，不为 UI Design System 的每个示例机械建状态。
- 多步骤异步、合法状态转换复杂或需要恢复/补偿时才使用状态机；普通页面不引入。
- 技术方案需要状态图时，标明节点、触发事件、守卫、终态和恢复；简单局部状态用表格即可。

## API、路由、样式与副作用

- API 边界遵循项目已有数据访问模式，组件不绕过统一认证、错误和类型契约；具体目录名由 Architecture 决定。
- 只描述新增或变化的请求、缓存/失效、并发和错误呈现；无变化时引用现有入口。
- 路由只在 URL 或导航行为变化时设计，明确鉴权、参数真源和兼容影响。
- 样式复用语义 token 和既有组件；新增 token 走 Design System 变更，不在业务组件建立旁路风格。
- 计时器、订阅、监听、并发请求和乐观更新必须说明建立、取消、竞态及失败恢复。
- 框架特定语法、Store、Router 和 CSS 工具只从当前 technology Profile 加载。

## 质量属性：按影响触发

| 质量属性 | 触发条件 | 最小设计要求 |
|----------|----------|--------------|
| 可维护性 | 始终适用 | 组件/状态所有权与变更边界清楚 |
| 可访问性 | 用户交互变化 | 继承项目基线并覆盖新增交互语义 |
| 性能 | 首屏/包体/长列表/媒体/高频交互受影响，或 PRD 有指标 | 给出现状、预算、策略和浏览器验证 |
| 安全 | 富文本、敏感数据、权限或新输入边界 | 明确前后端责任，不把客户端校验当安全边界 |
| 埋点 | PRD 需要验证行为假设或结果 | 事件与决策用途对应，不为“完整”采集 |
| 离线/降级 | PRD 或 Architecture 要求，或引入不稳定依赖 | 定义用户可理解的行为和恢复 |
| 国际化/响应式 | 目标用户、设备或项目基线要求 | 只覆盖本次变化及受影响断点/文案 |

不得无条件承诺统一 LCP 数字、设备宽度或运行时形态；这些阈值来自项目 Architecture、Design System Profile 或本次 PRD。

## 技术方案结构

### 必填核心

每份新建前端技术方案必须先声明唯一一行 `technical_design_contract_version: 1`，再使用以下五个名称作为二级章节（`##`），每章恰好一次且包含本次变化的实际内容；Runtime 在 Review 发布前执行相同结构门禁。该版本标识只约束新产物，不把迁移前历史文档误判为新版结构。

1. **来源与约束回读**：Story/AC、PRD 行为、设计决策、Architecture/technology 基线和非目标。
2. **现状与最小变更**：已有页面/组件/状态/API，保持/修改/新增/删除及新增理由。
3. **组件与状态所有权**：受影响组件树、职责、状态真源、数据流和必要状态转换。
4. **契约与验证**：API/路由/样式变化，AC → UI 行为 → 实现位置 → 浏览器/测试证据。
5. **风险、回退与未决项**：只记录影响交互、兼容或交付的内容。

### 条件章节

性能、埋点、离线/降级、国际化、响应式、安全、状态机和 Design System 扩展仅在触发后出现。未触发时继承项目基线，不创建空章节。

### 增量复杂度清单

新增页面、共享组件、全局状态、路由、依赖或 token 时，逐项写明 Story/风险来源、真实消费者、未复用现状的原因和验证方式。无法追溯的新增项应删除。

## AI 执行协议

**允许工具**：文件读写/搜索、只读探索、当前技术栈的设计参考 | **禁止**：代码修改

**自检**：

- PRD/设计与组件、状态、契约和验证双向可追溯。
- technology Profile 正确，没有把 Vue/Pinia 等默认示例强加给其他栈。
- 状态有单一真源和最近拥有者，无重复可写副本。
- 共享抽象有真实消费者和稳定语义，没有万能组件或推测性扩展。
- 性能、安全、埋点等专项均由明确影响触发并可验证。
