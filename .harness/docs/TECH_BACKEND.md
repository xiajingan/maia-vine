# 后端技术方案规范

> 专用于 `backend-design` 任务。技术方案必须服从本次 PRD/AC 和项目 `ARCHITECTURE.md`，以最小系统变更满足当前问题；编码基线见 [CODING_BACKEND.md](CODING_BACKEND.md)。

**产出物**：保存至 `docs/tech-docs/`，更新项目自有的作用域注册表 `index.md`，以 backend 类型登记模块、实际涉及的表/API/组件和 Story/AC。

**文档边界**：单份不超过 500 行，禁止用大段实现代码代替设计。只写本次变化和必要决策；Architecture 已提供的分层、横切能力与默认实现只声明复用，不复制设计。

**渐进式加载**：先按技术方案索引的模块、表/API、组件和 Scope Key 找到 current(`ready`/`done`) 条目，再读本次 PRD、`ARCHITECTURE.md`、受影响代码和强相关历史方案。当前实现与本次方案是设计依据，不为历史文档保持错误兼容。

**版本边界**：每个 Sprint 仅有一份 backend 技术方案，多模块在同一文件组织；Coding 修订当前文档，不新增补丁版。新 Sprint 不改写旧 Sprint 的方案。当前 Task/Run 登记 draft；Agent Review PASS 后等待人工确认方案及架构修改，再由 Runtime 发布 Ready。历史版本保存在 Runtime 快照中，索引与正文状态一致。

正文不再复制“作用域清单”；机器检索范围在索引维护。接口/模型定义归属具体模块，业务规则定义一次，其他层引用。

## 最高原则：最小充分技术设计

1. **需求保真**：每个技术变更关联 PRD 行为或 AC；不以技术偏好扩大产品范围。
2. **Architecture 贴合**：复用项目已选分层、协议、中间件和横切能力；偏离必须有当前需求或风险证据。
3. **增量优先**：先描述现状与最小差异，优先修改已有模块和契约。
4. **复杂度最低**：同样满足正确性与质量目标时，选择新增模块、状态、依赖和运行部件最少的方案。
5. **扩展有据**：只为已确认的第二实现、消费者或变化方向设计扩展点；未知未来只保留清晰局部边界。
6. **横切复用**：日志、Trace、安全、配置、审计和中间件接入优先继承 Architecture Provider，不在业务方案内重造。
7. **验证闭环**：关键设计决策必须有可执行或可观察的验证方式。

正确满足已确认 AC、有效架构和质量约束是共同边界；在满足边界的方案中，选择职责清晰、规则集中、累计维护成本最低的设计。

## 建模方式选择：战略 DDD 默认，战术 DDD 条件化

所有方案都应使用统一业务语言、明确领域/数据所有权和跨域契约，这是战略 DDD 的基本要求。实现结构由领域复杂度和项目 Architecture 决定。

| 模式 | 适用条件 | 避免 |
|------|----------|------|
| 简单数据操作 / Transaction Script | 单实体 CRUD、规则少、事务边界直接 | 为每张表创建 Aggregate/Domain Service |
| 领域模型 | 多对象共同维护不变量、规则被多个用例复用 | 只有 getter/setter 的贫血“领域层” |
| 状态机 / 工作流 | 生命周期、合法转换、补偿或长流程复杂 | 用散落布尔值表达状态 |
| 事件驱动 | 已有异步边界、多个真实消费者或明确解耦需求 | 为假想消费者提前引入 MQ/Event Sourcing |

Controller/Service/Repository 是可选的简单分层，不等同于 DDD。若 `ARCHITECTURE.md` 选择 domain/application/ports/adapters 等结构，技术方案和 Lint 必须服从项目声明，不得强制套用固定层名。

领域建模只在需要时说明：聚合/一致性边界、不变量、领域服务、领域事件和 Repository Port。Repository 围绕领域或数据访问需要设计，不按数据库表机械创建。

## 质量属性：由风险触发，不平均用力

| 质量属性 | 触发条件 | 最小设计要求 |
|----------|----------|--------------|
| 复杂度 | 始终适用 | 列出新增概念/依赖/运行部件及必要性，删除无来源项 |
| 可维护性 | 始终适用 | 职责、依赖方向、变更边界与验证入口清楚 |
| 扩展性 | 已知变体、第二消费者或明确 Roadmap | 只抽象稳定差异点，写明当前消费者 |
| 可观测性 | 新关键链路、外部调用、异步流程或新失败模式 | 复用 Provider，定义必要日志/metric/span 与关联 ID |
| 性能/并发 | PRD/Architecture 有 SLO、容量或热点风险 | 给出现状基线、负载假设、目标和验证；无证据不加缓存/队列 |
| 安全 | 新信任边界、权限、敏感数据或不可逆操作 | 明确主体、资源、动作、校验点和审计；复用安全基线 |
| 可靠性 | 重试、并发写、外部副作用或长事务 | 按语义选择超时、幂等、重试、补偿或拒绝策略 |

不得把“高性能、高并发、高扩展”作为没有容量模型的口号。缓存、异步化和冗余数据会增加一致性与运维成本，只有证据表明收益大于代价时使用。

## 公共能力归属

新增能力先按所有权分类，不能把所有可复用代码放进一个 `common` 包。

| 能力 | 公共技术 Library 可拥有 | 领域契约/业务工程拥有 |
|------|-------------------------|----------------------|
| 错误 | 错误信封、基础异常、序列化协议 | 业务错误码、消息与处理语义 |
| Event | envelope、发布接口、Trace 元数据 | 领域事件类型、字段和兼容策略 |
| 状态值 | 通用协议状态（确有跨域语义时） | 业务状态与合法转换 |
| 配置 | 加载、校验、刷新机制 | 业务配置项和默认值 |
| 上下文 | request/trace/tenant 等稳定载体 | 业务身份、授权策略和领域数据 |
| 安全/加密 | KMS/算法/脱敏等技术适配 | 数据分类、授权规则、密钥用途 |
| 审计/OTel | 写入、传播、导出和标准初始化 | 业务审计事件与业务指标语义 |
| Redis/数据库 | 连接、配置、健康与遥测适配 | Repository、查询、Schema、缓存一致性策略 |

提取跨工程 Library 必须满足：Architecture 指定平台 Provider，或存在多个已确认消费者；契约稳定、可独立测试、可版本化替换且不依赖消费者业务。只有潜在复用时先留在拥有该语义的工程内。

若依赖矩阵已有 Provider，必须复用；扩展 Provider 时写明 capability ID、Provider、协作路线、消费者契约和精确版本。业务适配留在消费者，禁止复制 Provider 源码。

## 接口、数据与基础设施设计原则

### 接口

- 只定义新增或变化的外部契约、边界模型、错误语义和兼容性。
- 认证方式、响应 envelope、分页等继承 Architecture；本次无变化时不重新设计。
- 幂等由操作语义、重试来源和副作用风险决定，不默认绑定 Redis 或固定 TTL。
- 破坏性变更必须有版本、迁移或消费者同步策略。

### 数据

- 涉及数据库或业务 ID 时必须读取 [Golden Rules G-9～G-11](GOLDEN_RULES.md#g-9g-11-适用边界与验证)，从当前 Architecture 继承数据库/方言版本、ORM/query builder、允许/禁用能力和 ID 契约；缺失项在本轮方案的“来源与约束 / 架构修改说明”中明确，不能自行默认具体产品。
- 明确数据所有权、不变量、事务边界和迁移/回退影响。
- 授权、状态迁移、业务校验、计算口径与编排明确到领域/应用代码所有者；数据库承担已声明范围内的查询、事务和声明式完整性约束，不引入隐藏的数据库业务执行。
- 查询、ORM 实际输出、分析、迁移及自有运维 SQL 均按声明的兼容边界设计；原生 SQL 集中并参数化，验证覆盖实际目标数据库的行为，不以 ORM 类型检查代替兼容证据。
- 业务 ID 明确生成方、唯一性范围、存储/传输类型、跨语言精度和恢复语义；涉及生成或序列化变更时，在对应模型与验证方式中写明端到端往返及适用的节点/时钟/重启测试。外部 ID、业务去重键与观测标识分别定义。
- 外键、JOIN、索引、冗余和一致性策略依据项目数据库基线与实际查询模型决定。
- 性能判断必须基于查询计划、容量或 SLO，不使用统一慢查询数字替代分析。

### 数据迁移

迁移方案归属**包含该数据迁移的迭代技术方案**，写在第三章对应数据对象与流程下；Architecture 只保留数据库、工具及兼容边界，部署文档承载执行命令与运行环境。既有数据的搬迁、回填、转换、清理及影响数据的结构演进均适用以下要求。

- 明确源/目标版本、迁移范围、字段与 ID 映射、转换规则、源数据快照或增量截止水位，以及切换、失败中止和恢复条件。
- 审查工具生成的实际 SQL；迁移执行互斥、可追踪，已应用迁移不可改写。明确幂等重跑、部分完成状态识别及续跑/补偿/恢复路径，并安排故障验证；按目标数据库的 DDL 事务语义设计，不能将外层事务等同于整批可回滚。不在多实例应用启动时并发推送 Schema；生产执行经审查、版本化的迁移文件，不直接用工具的 Schema push/自动同步代替迁移。
- 方案必须包含下表四类校验的对象、检查方法或脚本入口、输入与预期结果、通过标准；实现阶段执行并将结果留在测试/Review 记录。生成迁移文件或 ORM 类型检查通过均不能代替校验。

| 必备校验 | 方案与验收要求 |
|---|---|
| **目标 DDL checklist** | 从目标模型逐项列出全部受影响的表、列类型/长度/精度、可空性、默认值、主键/唯一键、索引、关联约束及字符集/排序规则；不适用项注明原因。逐项对应生成/补充的 DDL，并用迁移后真实数据库元数据核对，保证预期目标、实际 SQL、落库结构一致，不能只核对 ORM 声明。 |
| **源端模拟数据验证** | 在与源 Schema 一致的隔离验证库中创建模拟数据，经真实迁移入口转换后与明确的目标预期逐字段、逐关系核对完整性和准确性；覆盖正常、边界、空值/默认值、异常数据，以及适用的租户隔离、ID 精度和关联关系。预期结果依据转换规则独立定义，不能由待测迁移程序自行生成。 |
| **迁移结果对账** | 固定同一源范围与截止水位，验证 `源数据总数 = 目标数据总数 + 已知错误数据总数 + 未知错误数据总数`，并按源标识核对集合覆盖、互斥与重复，不能只比较净总数。已知错误须有逐条标识、原因和既定处置/验收规则；未处理、无法归类或无法定位的差异计入未知错误，通过时未知错误必须为 0。 |
| **目标数据逆向校验** | 从实际迁移后的目标数据抽样，覆盖各转换规则与边界，执行明确的逆向降级转换，与同一水位的源记录逐字段、逐关系比较一致性；记录样本标识、逆向规则及差异。发生合并、去重或有损转换时须保留还原必需的来源映射/原值，不能以“不可逆”豁免，也不能以备份存在或直接读取源记录冒充逆向转换。 |

对账中一对一转换按记录数计算；一对多拆分、多对一合并时，“目标数据总数”按**目标映射所完整覆盖的成功源记录数**计算，另列目标物理行数及预期基数校验，避免把不同计量单位代入上述等式。逆向比较允许的表示规范化须预先列明，不能忽略业务字段差异；逆向校验能力不等于可以直接在生产执行回退。

发布迁移执行遵守 [MIGRATION.md](MIGRATION.md) 的 checkpoint 与失败恢复协议，运行中的失败不自动触发数据回滚；四类数据校验不被发布脚本的格式/语法检查替代。

### 缓存、队列与外部依赖

- 默认不新增；先证明直接实现不能满足目标。
- 采用时说明数据真源、一致性/失效、失败语义、容量、观测和降级。
- 重试只用于可安全重试的失败；次数和退避来自依赖契约与时延预算。

## 技术方案结构

标题前声明 `technical_design_contract_version: 2` 和 `document_status: draft`。正文仅有以下三个二级章节，按顺序且各一次；细分对象使用三级及以下标题。Runtime 校验结构，Review 判断设计质量。

### 1. 来源与约束

来源到落地只维护一张简表：

| USER_STORIES | PRD 行为/流程 | 模块/领域 | 接口/模型/处理流程 | 改动点 | 验证方式 |
|---|---|---|---|---|---|

改动点写明具体对象和变化，不以任务号、attempt 或检查清单替代设计。后端验证方式说明接口、数据、单元测试或必要日志中的可观察结果。

1.2 为“架构修改说明”：`架构位置 | 当前设计 | 修改必要性 | 修改内容`。列出所有长期设计变化，无变化时引用沿用位置。技术方案读取当前架构作基线，获准后单向更新唯一架构；不并立第二份当前架构。

### 2. 现状与最小变更

只维护一张表：`对象 | 决策 | 变更说明与原因`。对象为可定位的模块、类、领域实体、表、接口、方法、页面、组件或状态结构；决策为保持、修改、删除、新增，说明实际参数、字段、流程、职责或模式变化与原因。

### 3. 建模与核心流程

按对象展示变更后的软件设计，并明确相对当前定义的变化：模型写字段、类型及关键关系；接口写输入/输出与行为；事件写最新定义、发布者、消费者及处理变化；流程采用流程图、时序图或泳道图；模式说明参与类/模块、职责与采用原因。

按需选择表达方式，不要求每项同时画全部图。关键异常、兼容、恢复和未决项写在相关对象旁；测试执行矩阵、诊断样本和检查结果留在已有测试/Review 记录，不生成第四章。

### 审查与发布

检查领域边界、规则所有者、第三方适配边界、模型/接口/流程一致性及累计维护成本。新增抽象必须集中真实变化点；禁止为修复局部样本不断叠加状态与运行机制。
架构变化使用 `task-context.architecture.candidate_path` 准备候选并由 `task-review --architecture-candidate` 绑定；人工同时批准后 Runtime 发布。不得提前覆盖有效架构；共享架构基线变化时先合并并重审。
统一人工确认、单文档修订及发布协议见 [DESIGN_GOVERNANCE.md](DESIGN_GOVERNANCE.md)。Ready 允许 Coding；Done 仅表示实现验证及架构核对已完成。

## AI 执行协议

**允许工具**：文件读写/搜索、只读探索、项目语言的设计参考 | **禁止**：代码修改

**自检**：

- Story/AC、PRD、Architecture 和技术变更双向可追溯，无新增产品语义。
- 已选择成本最低的适用建模方式，没有机械套用 DDD 或固定分层。
- 所有新增复杂度有当前需求或风险证据；扩展点有真实变化来源。
- 质量属性只在触发后展开，并给出目标与验证，不写口号。
- 公共技术能力与领域语义所有权分离，已有 Provider 未被重复实现。
- 涉及数据迁移时，方案包含目标 DDL checklist、源端模拟数据、结果对账和目标逆向校验四项，以及部分完成后的恢复路径。
