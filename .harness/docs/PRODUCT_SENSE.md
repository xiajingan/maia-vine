# Product Sense

> 面向产品任务的判断与转译规范。专用于 `product` 任务类型。
> 项目愿景、产品策略、用户场景与业务约束以根目录 `USER_STORIES.md` 为真源；本文件不替项目发明产品主张。

**产出物**：PRD 保存至 `docs/product-specs/[feature-slug].md`，更新项目自有的作用域注册表 `index.md`，关联 Story/AC ID。

**文档边界**：单份 PRD 不超过 500 行；行数不是完整性的目标。只描述本次行为增量和必要上下文，超出时按可独立验收的行为拆分。

**渐进式加载**：先用 `docs/product-specs/index.md` 的模块、页面/功能区域和 Scope Key 定位 current(`ready`/`done`) 条目，再读关联 Story、受影响现状和强相关历史 PRD。新 PRD 必须说明对当前行为的保持、细化、变更和排除；历史 PRD 不是本次实现真源。

**版本边界**：新 Sprint 创建新 PRD，不改写旧 Sprint 产物。Exec 以当前 Task/Run 登记 `draft`，覆盖同一 Scope Key 时通过 `Supersedes` 指向当前 Entry ID；Agent Review PASS 后等待人工审核；人工通过后由 Runtime 原子发布为 `ready` 并将被覆盖条目标为 `stale`。

## 规则语义与优先级

| 类型 | 含义 | Review 处理 |
|------|------|-------------|
| 不变量 | 跨项目始终成立的边界，如需求可追溯、不得虚构事实 | 违反即阻断 |
| 项目决策 | `USER_STORIES.md` 声明的产品策略、场景和约束 | 对当前项目是硬约束 |
| 条件规则 | 仅在对应风险或场景出现时适用 | 触发后检查 |
| 品味启发 | 帮助作判断的经验，不是固定答案 | 可有理由偏离 |

冲突优先级：**明确的 Story/AC 与外部约束 > 项目产品策略 > 当前场景证据 > 通用品味启发**。不得用框架偏好覆盖项目输入。

---

## 最高原则：最小充分设计

目标是在不漂移用户场景的前提下，以最小产品和实现代价产生可验收价值。

1. **问题保真**：保持使用者、上下文、触发、困难、期望结果与非目标。
2. **结果优先**：先定义用户可观察结果，再选择交互和功能形态。
3. **增量优先**：优先调整已有能力；新增概念必须解释现状为何不能承载。
4. **证据触发**：不为未知用户、假想异常或推测中的未来需求增加功能。
5. **复杂度守恒**：同样满足 AC 时，选择新增页面、步骤、状态和规则更少的方案。
6. **按风险展开**：只展开与本次行为和风险有关的状态、指标、文案及异常。
7. **允许未知**：影响范围的未知项必须显式记录；不得通过“三次为什么”或 JTBD 编造动机。

### 最小化不等于简陋

- 不得删除完成主路径所需的反馈、权限、恢复或关键边界。
- 不得把复杂度转嫁给用户、客服、运维或后续实现者。
- 不得用“以后再做”回避本次 AC 明确要求的结果。

## 场景解构、抽象与防漂移

### 需求接入

用户在 Chat 中直接提出的新需求不是 PRD 的旁路输入。产品工作开始前，编排者必须先通过 `harness requirements intake` 将原始输入整理为 `draft` Story；只能补全输入可证明的内容，缺失信息显式保留为待确认。新版需求确认与精确 US/AC 选择采用 [DESIGN_GOVERNANCE.md](DESIGN_GOVERNANCE.md) 的宿主用户事件协议；缺少有效批准时不得进入产品任务，手写 Ready 不能旁路。

### 场景内核回读

PRD 开始前必须从 Story 原文回读以下内容，不足时保留为待确认项：

`使用者 → 上下文/触发 → 当前困难 → 期望结果 → 约束 → 非目标 → AC`

### 允许的转译操作

| 操作 | 说明 | 记录要求 |
|------|------|----------|
| 保持 | 原样继承 Story 语义 | 标明关联 Story/AC |
| 细化 | 增加字段、状态、文案和边界 | 不改变原结果 |
| 重组 | 将场景组织为流程或功能结构 | 保留双向追溯 |
| 有意变更 | 改变输入语义或结果 | 写明原因、影响和确认来源 |

PRD 不得把技术分层、接口、表结构或缓存策略包装成用户需求。技术实现不确定时只描述行为契约。

### 最小范围与追溯矩阵

该矩阵是 PRD 唯一的规范性范围清单；正文只能解释已登记的 Scope ID，不得旁路增加产品行为。

| ID | 系统/模块 | 产品行为 | 新增复杂度 | 必要性/未复用原因 | 来源 | 验收观察 |
|---|---|---|---|---|---|---|
| SCOPE-001 | 业务模块 | 本次改变的业务行为 | 无或必要的新概念/步骤 | 修改必要性与复用判断 | US-001 / US-001-AC-01 | 用户可理解的结果 |

- ID 在本文唯一且稳定；正文不复制 Task/Run、Scope Key 等机器字段。索引文件链接以 `#SCOPE-001` 关联范围 ID，保留跨迭代稳定的 Scope Key。
- 来源只引用本 Sprint 人工选中的 Story/AC，完整覆盖选择集合；Architecture 约束只能作为产品需求的附加来源。non-product-change 按规划协议引用明确的 Architecture 章节。
- 系统/模块按产品职责组织，行为、影响、必要性和验收均为产品表达，不写函数、数据库状态或厂商错误分支代码。
- 新增复杂度写“无”或简明说明实际新增概念；不强制分类编码。无映射内容删除或列为非目标，不进入产品范围。

## 产品判断工具箱（按需使用）

| 工具 | 适用触发器 | 不应机械使用的情形 |
|------|------------|--------------------|
| JTBD | 动机、替代方案或真正竞争对象不清楚 | Story 已有明确行为修复或合规要求 |
| 三次为什么 | 表述停留在表面功能且范围会受动机影响 | 会诱导 Agent 猜测用户动机 |
| 价值闭环 | 跨步骤、跨角色、转化或长期价值链路 | 单点纠错、内部规则调整 |
| 断裂点分析 | 外部依赖、异步等待、不可逆操作或关键链路 | 为所有理论异常设计降级系统 |
| 注意力分析 | 首次使用、复杂流程、等待或高认知负担 | 后台批处理、纯 API 消费者 |
| 数据埋点 | 需要验证行为假设或业务结果 | 已有观测足够或无决策用途 |

使用工具必须产生决策；只复述模型、但不改变范围或验收的内容应删除。

## 通用品味启发

以下是默认判断，不是不可摇摆的项目策略：

- **清晰胜过聪明**：用户应理解当前状态、可执行动作及主要后果。
- **一致胜过新奇**：同一语义优先复用已有交互、文案和反馈模式。
- **默认值表达判断**：存在默认值时说明它服务谁、承担什么代价；无证据时不伪造强默认。
- **状态服务行动**：只定义用户可遇到且需要理解或恢复的状态。
- **渐进披露**：复杂度随任务需要出现，不把专业用户必需控制项一概隐藏。
- **可逆性匹配摩擦**：低风险操作减少阻力，高风险或不可逆操作增加确认与证据。

具体性能阈值、步骤数、设备基线、文案语气和入门曲线必须来自项目策略、PRD 验收或 Architecture，不能由本文件统一假定。

## PRD 最小结构

PRD 标题前声明受 Runtime 管理的 `document_status: draft`，正文仅使用以下四个二级章节，不新增通用验证、风险或异常章节：

1. **场景与目标**：场景内核、产品目标、系统定位。涉及第三方时说明系统间职责、依赖能力及交换数据；约束、假设/待确认项、非目标分别用列表，每项一个清晰判断。
2. **最小范围与追溯矩阵**：使用上方七列，唯一维护范围与验收观察；删除重复 AC 验收章节。
3. **行为与流程**：按“关联范围 → 参与者职责与关系变化 → 流程图 → 核心变化”组织。业务数据流用泳道图，泳道可为系统、子系统、模块或领域实体，节点表达数据处理，连线标注数据/事件；业务旅程用模块流程节点表达触发、动作和结果。异常与恢复嵌入对应节点，不穷举技术错误。未改变流程的纯文案调整可引用既有流程。
4. **影响面与保持项**：仅描述实际受影响的业务、架构、UI 风格、数据、性能、安全和横切能力；指标有来源，未影响的分类不机械扩写。

图文使用业务名称；接口文档编号、错误码、HTTP 状态与内部状态必须区分，诊断样本和执行轮次归入测试/运行记录。结构校验不能替代语义 Review。

PRD 必须先通过 Agent Review，再由人工审核当前版本，发布为 Ready 后才能进入依赖的 UI 或技术设计。正文、索引和批准版本须一致，统一协议见 [DESIGN_GOVERNANCE.md](DESIGN_GOVERNANCE.md)。

## PRD 自检

1. **输入保真**：场景内核、约束和非目标未漂移；假设没有被写成事实。
2. **最小充分**：所有内容均服务 AC 或明确风险；不存在为完整模板而生成的功能。
3. **增量明确**：当前行为与目标差异清楚，新增项有必要性说明。
4. **可实现可验收**：没有阻塞性产品歧义；QA 能据行为结果设计验证。
5. **条件适用**：使用的产品工具和专项章节均写明触发原因。

## 产品品味沉淀机制

新的产品规则不得因一次成功案例直接升级为通用约束。候选规则至少记录：

`问题｜适用场景｜建议决策｜收益｜代价｜反例/不适用条件｜证据｜成熟度`

成熟度依次为：**观察 → 候选启发 → 多场景验证启发 → 不变量/项目可配置规则**。外部方法论只能作为候选证据；实际用户行为、项目复盘和 Boss 决策优先。只有跨项目稳定且可机械判断的规则才进入 task-rules 或 Lint。

## AI 执行协议

**允许工具**：文件读写/搜索、只读探索 | **禁止**：bash 执行、代码修改

1. 原始需求尚未进入 USER_STORIES 时先执行需求接入；已有 Story 时回读其场景内核、产品策略、约束、非目标和 AC。
2. 检查现状，区分保持、细化、重组与有意变更。
3. 选择满足 AC 的最小产品增量，删除无来源的功能。
4. 仅在触发条件成立时使用 JTBD、价值闭环、断裂点等工具。
5. 建立 Scope → Story/AC 或 Architecture 来源 → 行为 → 验收观察追溯。
6. 在 Scope 行记录会改变结果的假设、取舍和新增复杂度。
7. 执行五项自检并更新产品索引。
