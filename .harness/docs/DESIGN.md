# Design

> 专用于 `design` 任务。设计必须保持 PRD 的用户场景和可观察结果，以最小交互与视觉变更解决问题。
> 产品判断见 [PRODUCT_SENSE.md](PRODUCT_SENSE.md)；项目采用的 token、组件和交互 Profile 见 [UI_DESIGN_SYSTEM.md](UI_DESIGN_SYSTEM.md)。

**产出物**：设计文档保存至 `docs/design-docs/[feature]-design.md`，更新项目自有的作用域注册表 `index.md`，关联 Story/AC ID；受影响页面提供可对照的 HTML 原型或 PNG 设计稿。

**渐进式加载**：先按设计索引的模块、页面/功能区域和 Scope Key 找到 current(`verified`) 条目，再读本次 PRD、UI Design System、受影响现状和强相关历史设计。当前实现与本次已验证设计是基线，不复制无关历史页面。

**版本边界**：新 Sprint 创建新设计文档，不改写旧 Sprint 产物；Exec 以当前 Task/Run 登记 `draft` 并用 `Supersedes` 指向 current Entry，Review PASS 后由 Runtime 发布并更新旧条目状态。

每份设计文档必须包含唯一的 `## 作用域清单`，并与 `docs/design-docs/index.md` 当前 Task/Run 登记逐行一致：

| Scope Key | 模块 | 页面/功能区域 |
|-----------|------|---------------|
| design:example | example | example-area |

## 最小充分设计原则

1. **场景保真**：每个页面、步骤、状态和文案关联 PRD 行为或 AC。
2. **现状优先**：优先调整已有信息架构、页面和组件；新增入口必须说明现状不能承载的原因。
3. **决策负担最小**：减少与当前任务无关的选择，不机械限制专业任务必需步骤。
4. **一致性优先**：相同语义复用项目既有组件、反馈和文案模式。
5. **状态按需**：只设计用户可遇到且需要理解、决策或恢复的状态。
6. **工程可落地**：视觉映射到项目 token/组件 Profile，复杂度与实现收益匹配。
7. **可逆性匹配摩擦**：低风险操作减少阻力；高风险或不可逆操作提供确认、证据和恢复。

固定步骤数、LCP、设备宽度、动效时长、首屏 CTA 数和埋点要求必须来自项目产品策略、UI Design System Profile、PRD 或 Architecture，不能作为所有设计的统一答案。

## PRD 到设计的转译

1. **回读**：提取场景内核、目标行为、AC、约束与非目标，不补写产品动机。
2. **现状对照**：确认现有入口、页面、组件和已支持状态，识别最小行为差异。
3. **交互设计**：覆盖受影响主路径和真实边界；每步说明用户输入、系统反馈和结果。
4. **视觉表达**：用层级、对比、留白和组件状态表达业务优先级，复用项目 token。
5. **设计验证**：PRD/AC → 页面行为 → 原型画面一一对应，并与前端确认实现成本。

允许的变化只有：保持、细化、重组和有意变更。有意改变 PRD 行为时必须回到产品任务确认，不能由设计阶段静默决定。

## 状态与交付深度

[UI_DESIGN_SYSTEM.md §5](UI_DESIGN_SYSTEM.md) 提供稳定状态目录，不代表每个页面必须生成全部状态。设计文档应建立适用性矩阵：

| 状态 ID | 是否可达 | 触发条件 | 用户需要理解/执行什么 | 画面/复用来源 |
|---------|----------|----------|------------------------|---------------|
| <!-- Sx --> | <!-- 是/否 --> | <!-- TODO --> | <!-- TODO --> | <!-- TODO --> |

- 正常态和本次变化直接影响的状态必须有设计证据。
- 不可达状态写明原因即可，不生成占位画面。
- 已由现有组件完整覆盖且本次不改变的状态可引用现状，不重复绘制。
- 外部依赖、异步等待、权限、离线和局部失败只有真实可达时才纳入。

## 交付结构

### 必填核心

1. **来源与约束回读**：Story/AC、PRD 行为、项目设计基线和非目标。
2. **现状与最小变更**：保持/修改/新增/删除的页面与组件，新增理由。
3. **页面流与交互**：受影响主路径、必要边界、输入/反馈/结果。
4. **状态适用性与视觉规格**：适用状态、组件行为和 token 映射。
5. **追溯与验证**：AC → 页面/状态 → 原型或现状证据 → 核心比对点。

### 条件交付

| 内容 | 触发条件 |
|------|----------|
| 完整异常/恢复流 | 新失败模式、不可逆动作或外部依赖 |
| 响应式画面 | 目标设备或受影响断点变化 |
| 动效规格 | 动效解释状态变化或影响操作结果 |
| 埋点 | PRD 需要验证行为假设或结果 |
| 新组件状态板 | 新增/改变共享组件契约 |
| 新 token | 现有语义 token 无法表达且 Design System 变更获准 |

未触发的内容不创建空表。数据示例只覆盖受影响内容类型、边界和状态，不为项目无关媒体类型凑矩阵。

### 增量复杂度清单

新增页面、步骤、共享组件、状态、交互模式或 token 时，列出其 Story/风险来源、未复用现状的原因和验证画面。无法追溯的新增项应删除。

## 质量自检

- PRD/AC 与页面、状态和设计证据双向可追溯，没有新增产品语义。
- 方案是满足行为结果的最小交互增量，没有为模板完整性生成页面或状态。
- 复用了项目既有信息架构、组件和 token；新增项有明确必要性。
- 用户在受影响路径上能理解当前状态、下一动作和关键后果。
- 条件交付均有触发依据，工程实现成本和回归范围明确。

## Boss 设计走查（项目可配置）

`config/harness.yml.gates.ui_design_l3: true` 且 Sprint 实际列入 `design` 时，design Review PASS 后必须由 Boss 批准 `docs/design-docs/sprint-N-design-approval.yml`；backend-only 影响面不触发 UI L3。审批记录必须包含 `sprint`、`decision: approved`、`confirmed_by/confirmed_at/source`、`commit_sha`、当前 `planning_contract_sha256`，以及从当前 design attempt 抄录的 `design_reviews: [{task_id, report, sha256, recorded_at}]`。Runtime 验证摘要和 Git lineage，旧审批不能复用。

该配置为 `false` 时，design 保持 L1 + 独立 Review，不得因本文档自行追加 L3。最终产品行为仍在 `product-acceptance` L3 走查。

## AI 执行协议

**允许工具**：文件读写/搜索、只读探索、原型/设计稿工具 | **禁止**：代码修改

1. 回读 PRD/AC 和现状，确认最小设计差异。
2. 设计受影响主路径和真实可达边界。
3. 建立状态适用性矩阵，复用未变化的现状证据。
4. 输出受影响页面的可对照原型/设计稿和 token 映射。
5. 建立 AC → 页面/状态 → 设计证据追溯，执行质量自检。
6. 仅在项目启用 UI L3 时准备并等待 Boss 走查。
